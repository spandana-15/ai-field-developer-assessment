# AI Field Developer / Solutions Engineer Assessment

**Complete, locally runnable reference implementation of all four assigned stages**, written in Python. Customer data, refunds and model providers are deliberately mocked; no real financial action occurs and no external LLM credentials are needed.

## Quick start

Requires **Python 3.11+**. From the project directory:

```bash
python -m venv .venv
# macOS/Linux: source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -e '.[dev]'
python -m pytest -q
```

The official `mcp` 2.x package is needed for Stage 1. Installing from `pyproject.toml` installs it. If you only install the preloaded HTTP test packages, the Stage 1 wire-level test skips, while its pure validation tests still run.

Set an environment variable with a unique random secret (the HMAC signer used by the local mock authentication):

**macOS/Linux**

```bash
export ASSESSMENT_TOKEN_SECRET="$(python -c 'import secrets; print(secrets.token_hex(32))')"
```

**Windows PowerShell**

```powershell
$env:ASSESSMENT_TOKEN_SECRET = python -c "import secrets; print(secrets.token_hex(32))"
```

Run in terminal A:

```bash
python scripts/run_all.py
```

Run in terminal B **with the same secret environment variable**:

```bash
python scripts/demo_requests.py
```

To test Stage 1's **real stdio protocol**, independently run:

```bash
python scripts/stage1_demo.py
```

The stdio server itself is launched as a subprocess by the client. Do not run its command in a terminal expecting a human-readable prompt: it communicates via JSON-RPC over stdout, never print statements.

## Four stages and corresponding files

| Stage | Implementation | Interface | What is enforced |
|---|---|---|---|
| 1. Custom MCP server | `src/assessment/task1_mcp_server.py`, `task1_core.py` | Official MCP SDK over stdio | Two tools, strict Pydantic validation, `-32602` on malformed arguments, stderr-only logging |
| 2. MCP security gateway | `src/assessment/task2_gateway.py`, `auth.py` | `POST localhost:8101/mcp` | Signed bearer tokens, role-aware filtering of `admin_*`, HTTP/JSON-RPC forwarding, `-32001` denied |
| 3. Streaming PII guardrail | `src/assessment/task3_stream_gateway.py`, `task3_redactor.py` | `POST localhost:8103/v1/chat/completions` | SSE delta parsing, cross-chunk email/SSN/card redaction, Luhn card validation, bounded memory |
| 4. Model router and limiter | `src/assessment/task4_router.py`, `task4_limiter.py` | `POST localhost:8104/v1/completions` | Per-tenant 50,000-token rolling minute on disk SQLite, safe reservations, 429/3-second timeout fallback, sanitized errors |

`src/assessment/mocks.py` provides downstream endpoints at `localhost:8102` and controlled test scenarios; it is explicitly not a production MCP server. Stage 1 uses the official MCP SDK, while Stage 2 is a deliberately narrow HTTP/JSON-RPC reverse-proxy exercise as requested by the brief. They do not need to share the same transport to be assessed separately.

## Stage 1: MCP Server

The official MCP Python SDK v2 low-level `Server` API enables returning **standard JSON-RPC errors** rather than only returning `isError=true` tool results.

- `get_customer_record(customer_id: "CUST-00001")` returns a mock record.
- `trigger_refund(customer_id: "CUST-00001", amount: 25.50, reason: "Customer returned the item")` returns a **simulated** refund receipt.
- An invalid ID, missing/extra fields, nonpositive/nonfinite amount, boolean amount, or reason shorter than 10 non-whitespace characters is rejected with `-32602`.
- `stdio_server()` uses the protocol stream only; logger output goes to stderr.

Demo: `python scripts/stage1_demo.py`. The SDK validates the output protocol during connection, tool discovery, calls and error handling.

## Stage 2: MCP Authorization Proxy

A signed bearer token contains a short-lived `role` (`viewer` or `admin`) and `tenant`. Tokens are generated by:

```bash
python -m assessment.auth viewer
python -m assessment.auth admin
```

The header is `Authorization: Bearer <token>`. There is **no trust in an unsigned role header** or in a role supplied in the JSON request. `tools/list` is forwarded to the fixed mock downstream for authenticated clients; `tools/call` for `admin_*` rejects viewers locally (`-32001: Unauthorized Tool Call`) and is never forwarded. Non-admin tools can be called by both roles.

The proxy also handles JSON-RPC notifications and mixed batches. Note that this is **HTTP/JSON-RPC for the assessment**, not a general-purpose implementation of the full MCP Streamable HTTP session/streaming lifecycle.

## Stage 3: Streaming PII Guardrail

Input is a streaming chat completion request, with `"stream": true`. The upstream emits JSON SSE events such as:

```text
data: {"choices":[{"delta":{"content":"alice@exam"}}]}

data: {"choices":[{"delta":{"content":"ple.com"}}]}

```

The proxy **does not emit the sensitive fragments**. It buffers unfinished candidate tokens, checks emails, SSNs (spaced, dashed or undelimited), and Luhn-valid cards, then emits the same SSE delta shape containing `[REDACTED]`. Transport frames may themselves be cut across arbitrary byte boundaries, including UTF-8 sequences. The redactor keeps at most 512 pending plaintext characters; unusually long candidate runs are masked fail-closed, which intentionally trades a little fidelity for safety.

Streaming is incremental; it does not collect the full generated response. Initial safe text is flushed at safe delimiters, so some token-level delay is intentional to prevent leaking partial PII. This is a **pattern-based demonstration**, not a comprehensive DLP engine for all sensitive data or every locale.

## Stage 4: SQLite Token Quota + Failover

1. Validate a signed bearer token and extract the tenant from trusted claims.
2. Estimate prompt cost **conservatively** from UTF-8 bytes; reserve that amount plus `max_tokens` before making any provider request. Do not trust the caller to report its own cost.
3. In an atomic `BEGIN IMMEDIATE` SQLite transaction, evict events older than 60 seconds, sum the tenant's reservations, then admit/reject based on the **50,000 token/minute** quota. `WAL` mode supports cross-process connections.
4. Attempt the primary LLM, with a **3.0-second request timeout**. On HTTP 429, timeouts, or network availability errors, attempt the backup. A primary HTTP 500 is **not** considered an automatic failover trigger in this implementation.
5. Release reservations for unsuccessful requests. On success, settle down to trustworthy provider-reported `usage.total_tokens` when it is lower than the reservation. Errors use only standardized public strings, without upstream response bodies or tracebacks.

The SQLite database is written to `data/rate_limits.sqlite3` (or `RATE_DB_PATH`). It survives process restart. Its entries age out by their recorded wall clock. After exceeding the quota, clients receive HTTP 429 with `Retry-After`.

**Token-count accuracy note:** This assessment uses a safe, potentially overcharging admission estimate, since different upstream tokenizers count text differently. For a production gateway, replace `count_prompt_tokens` with the exact provider/model tokenizer and reconcile provider usage. SQLite is fit for this local assignment; a large multi-region system would likely use a distributed atomic quota backend instead.

### Mock provider failure modes

Use the model field in the Stage 4 JSON body:

| Model value | Primary behavior | Router behavior |
|---|---|---|
| `demo` | Returns 200 | Responds from primary |
| `force_429` | Returns HTTP 429 | Uses backup |
| `force_timeout` | Sleeps for 5 seconds | Times out at 3 seconds and uses backup |
| `force_error` | Returns HTTP 500 | Returns sanitized gateway error |

## Testing and submission

```bash
python -m pytest -q
```

Tests cover malformed IDs and refund values, invalid tokens, blocked admin requests, passthrough listing, mixed JSON-RPC batches, partial-byte SSE frames, cross-delta PII, bounded redactor memory, exact rolling-window expiry, SQLite settlement, 100 simultaneous quota reservations, timeout/429 fallback and upstream error sanitation.

Before submission:

1. Verify `python -m pip install -e '.[dev]'` installs all dependencies (including the official `mcp` package).
2. Run `python -m pytest -q`; confirm the Stage 1 stdio integration test **does not skip**.
3. Run `python scripts/run_all.py` and `python scripts/demo_requests.py` with a shared secret.
4. Confirm `python scripts/stage1_demo.py` connects and gets `-32602` for invalid inputs.

### Notes and limitations

- Mock refund actions never modify payment systems.
- Demo HMAC tokens are for this exercise, not production identity provisioning; a real deployment should validate OAuth/OIDC issuer, audience, scopes, expiry and keys, use TLS and external secret management.
- Do not use live customer PII in mock prompts/logs. Nothing here persists raw prompts or redaction content to SQLite.
- The four tasks are separate demonstrations rather than a production-ready combined gateway. See `docs/implementation_notes.md` for design and tradeoffs.
- SDK reference: [official MCP Python SDK](https://py.sdk.modelcontextprotocol.io/), [low-level server API](https://py.sdk.modelcontextprotocol.io/advanced/low-level-server/).
